# Security model

Principle: security must not depend on the code being secret. Everything except keys can be public.

Each defence below must have a test. If you add a defence, add its row here.

| Threat | Example | Defence | Test that proves it |
|---|---|---|---|
| Cross-tenant access (IDOR) | Org A token requests an org B vehicle id | `orgId` from verified token on every query; other-org resource returns 404 | Two-org seed; org A token on org B ids expects 404 |
| Broken access control | VIEWER calls a mutation | Per-route role allow-list in the auth hook | 403 test per disallowed role per route |
| Missing authentication | Request with no/invalid token | Auth hook returns 401 | 401 test per route |
| Credential stuffing / brute force | Repeated login attempts | 5 failures lock the account 15 minutes; per-IP rate limit | Login lockout test |
| Token theft | Stolen access token | 20-minute access token; rotating, hashed refresh tokens; revoke on deactivation or password change | Refresh rotation + revoked token tests |
| Refresh token replay / race | A stolen refresh token used after the real client rotated it, or two requests rotating one token at once | Atomic claim of the old token; replaying a rotated token after a 10 s grace revokes all of the user's sessions | Concurrent-refresh and reuse tests |
| Account enumeration | Telling real emails from fake ones by response or timing | Unknown emails pay the same bcrypt cost and lock after 5 failures exactly like real accounts | Login-enumeration tests |
| Privilege escalation by renaming | A regular admin renames themselves to the reserved super-admin name | Reserved name (case-insensitive) rejected on create, staff update and own-profile update | Reserved-name tests |
| Stale sessions after access change | Admin resets a password, deactivates or changes the role of a user who still holds a refresh token | Those edits revoke the user's refresh tokens in the same transaction | Session-revocation tests |
| Cross-tenant references | Creating a model under another org's brand | Parent ids are checked against the actor's org (404) | Parent-ownership tests |
| Foreign ids in a vehicle write | A vehicle created or edited with another org's model, hall, supplier, customer or row colour, so reading it back joins that org's data | Every referenced id is checked against the actor's org (400) before the transaction | Foreign-id tests for create and update |
| Server-side request forgery via file URLs | A "photo" URL pointing at an internal address, later fetched by the PDF export | New file URLs must be under the configured public base and inside the caller's org folder; stored URLs are re-checked before any fetch; no redirects, size and time caps, images only | Object-storage URL tests; file service fetch tests |
| Cross-org object deletion | A photo URL pointing at another org's file, so deleting the photo deletes the real object | Same URL rule on the way in; deletion only ever touches keys inside the actor's own org folder | File service deletion tests |
| Double processing | Two daily runs, or a run racing an edit, flip a vehicle to Shipped twice | The transition is a conditional update on the current status; reminders are de-duplicated per vehicle and event per day | Daily checks real-database test |
| Accidental real email | A developer or CI run with a stray key sends mail to real people | One module (`src/lib/email.ts`) makes the only Resend call; it does nothing without `RESEND_API_KEY` and `EMAIL_FROM`; tests delete both variables; a test fails if any other file mentions Resend | `tests/email.test.ts` |
| Token audience confusion | A staff token used on customer routes, or a customer token on staff routes | Separate secrets, `aud` (staff / customer) and `iss` checked by each guard; startup fails if the secrets are equal | `tests/customer-zone.test.ts` (forged tokens in both directions) |
| Customer IDOR | One customer reading or changing another's data, or another org's | Customer id and org come only from the verified token; every query filters by both; strict bodies reject id and org fields; the guard re-loads the account each request | `tests/customer-zone.test.ts` (two customers in one org, two orgs) |
| One-time code brute force | Guessing a 6-digit code, in parallel | 5 attempts, each reserved atomically before the comparison; 10-minute life; single use; HMAC-stored; per-email and per-IP limits | `tests/customer-auth.test.ts`, `tests/db/customer-auth.concurrency.db.test.ts` |
| Account enumeration (customers) | Telling real addresses from fake ones by response or timing | Identical answers, a bcrypt compare or hash on every branch, a response-time floor, limits that count unknown addresses | Equality, bcrypt-count and floor tests |
| Pre-registration takeover | Registering a victim's address with a password the attacker knows | Register stores no password; it is set together with the emailed code | Verify-email tests |
| Customer data in logs | Passwords, codes, tokens or addresses reaching logs | Nothing logs them; email notices are masked; strict bodies | `tests/customer-logs.test.ts` (real log output) |
| File gateway abuse (customers) | A customer asks for a photo or document that is private, belongs to someone else, sits on a vehicle they may not see, or is not an allowed type; or hammers the endpoint | Authorise first (own vehicle, same org, not deleted, export track, released; file released), then read; every failure is the same 404 and nothing is read from R2; only jpeg/png/webp/pdf are served; rate limits per IP and per customer | `tests/storage-signing.test.ts` (gateway block), `tests/db/milestones.db.test.ts` |
| Storage key / URL leakage | An R2 address, an object key, the account id or the public base reaching a customer response, header, error or log | Files are addressed by database id; the API streams and never redirects; the stored URL is never in a DTO; the redactor scrubs R2 hosts, keys and the account id from logged errors; storage errors are a generic 500 | `tests/storage-signing.test.ts` ("NO customer response or log line contains...", "a storage error is a generic 500...") |
| Content sniffing / active content | An uploaded svg or html file served to a customer's app or browser and run | Allowlist of jpeg, png, webp, pdf at upload and again at serve time; the extension is forced from the signed type; `nosniff`, a sandboxing CSP and `inline` only for images | `tests/storage-signing.test.ts` (content types, headers) |
| Hostile image bytes | A file named .jpg that is really an SVG with script, a decompression bomb, or a photo carrying GPS data, processed by the thumbnail step | The real format is read from the bytes and must be jpeg/png/webp; pixels capped before decoding; originals over 12 MB are not read; all metadata is dropped from the thumbnail; failure is generic and never fatal | `tests/thumbnail.test.ts` |
| R2 client pointed at the wrong endpoint | A misconfiguration sends requests (and credentials) to an AWS endpoint or an attacker's host | The endpoint is derived from a validated 32-hex account id; region `auto`; no AWS hostname in the code | `tests/r2-object-store.test.ts`, `tests/env-storage.test.ts` |
| Presign abuse | A client signs an upload for another org's vehicle, picks its own key or extension, or uploads a huge or wrong-type file | Vehicle ownership checked before signing; the server builds the key from a sanitised name with the extension of the signed type; the link pins size and type and lasts 300 s and requires no checksum headers; 10 MB images / 20 MB PDFs only; exact-match content types | `tests/storage-signing.test.ts` (presign block), `tests/r2-object-store.test.ts` |
| Double, lost or wrongly removed milestones | Two requests (or the job and a person) record the same milestone; a rolled-back change leaves one behind; clearing an ETD deletes something a person recorded | A unique key on (vehicle, type) with INSERT ... ON CONFLICT DO NOTHING in the status-change transaction; edits lock the vehicle row and decide from a fresh read; going down removes only milestones the system recorded and nobody touched, each with an ActivityLog row | `tests/milestones.test.ts` (every branch), `tests/db/milestones.db.test.ts`, `tests/db/milestones.concurrency.db.test.ts` (parallel set/clear of the ETD) |
| Backfill against the wrong database | The one-off backfill is pointed at production | It reads MIGRATION_DATABASE_URL only, is a dry run unless `--apply`, prints counts and the project ref only, and plans only milestones with a known date | `tests/milestone-backfill.test.ts` |
| Customer data leaking through a DTO | A response carries remarks, auction hall, costs, supplier or agent details, row colour, another customer's data or an internal id | Every DTO is built field by field from a narrow select; one shared "vehicles this customer may see" filter; sentinel values in the fake data are searched for in every response | `tests/customer-data.test.ts` (key sets, "never contains an internal value or an internal field name") |
| Amounts shown to customers | A price, an amount or a total purchase value reaches a customer response or a log (a business decision: customers see none) | The amount columns are not selected by any customer query; no customer DTO has an amount field; `sort=price` is refused; the staff `customer-info` body rejects amounts; the columns are unused and slated for removal (`docs/deferred/unused-columns.md`) | `tests/customer-data.test.ts` (sentinel amounts in every response and in the logs, exact key sets, `sort=price` is 400), `tests/customer-admin.test.ts`, `tests/db/customer-data.db.test.ts` |
| Customer read IDOR | One customer reading another's vehicle, timeline, photos or documents, or another org's | Every query starts from `customerVehicleWhere` (org, own id, released, export track, not cancelled, not deleted); an unknown, foreign or unreleased id is the same 404 | `tests/customer-data.test.ts` (ownership matrix on every route), `tests/db/customer-data.db.test.ts` (the same as SQL) |
| Vehicle-existence probing via link requests | Learning which serial numbers exist by asking to be linked | The request never looks the vehicle up; the same 202 for any serial; limits per IP and per customer; at most 20 pending | `tests/customer-data.test.ts` (link request block, including "never looks the vehicle up") |
| Scraping through list parameters | Large pages, unknown sort columns or filters used to dump data or probe columns | Page size capped at 50; sort limited to three fields; strict parameters; per-customer read limit (240/min) | `tests/customer-data.test.ts` (pagination, parameters are strict, rate limits) |
| Staff tools reached by the wrong role | An OPERATOR or VIEWER disables a customer, decides a link request or releases photos | Role lists live in one file (`config/roles.ts`) and are enforced in the auth hook per route | `tests/customer-admin.test.ts` ("access" matrix: 401, 403 per disallowed role with nothing changed, allowed roles pass) |
| Cross-org use of staff tools | An administrator of one org changing another org's customer, request, FAQ, vehicle, photo or document | Every lookup filters by the token's org; another org's id is 404 | `tests/customer-admin.test.ts` ("another org's id is 404"), mutation checks on the org filters |
| Disabled customer keeps access | A disabled account's refresh token, access token or device token still works | Disabling revokes every session and deletes device tokens in the same transaction; the guard re-loads the account on every request | `tests/customer-admin.test.ts` ("disabling ends every session"), `tests/db/customer-admin.db.test.ts` |
| Two customers claim one vehicle / double decision | Parallel approvals link a vehicle to two customers or decide a request twice | Conditional claims (`status = PENDING`, `customerId IS NULL OR same`) inside one transaction | `tests/db/customer-admin.db.test.ts` (15 parallel rounds each; both conditions proven necessary by mutation) |
| Releasing the wrong photos | A bulk release touches photos of another vehicle, or "all" is implied | Ids must all belong to the vehicle (else 404, nothing changes); an explicit list of 1 to 200 ids is required | `tests/customer-admin.test.ts` (bulk release), `tests/db/customer-admin.db.test.ts` |
| Link request outcome leaks vehicle existence | The rejection message or notification hints that a serial exists or belongs to someone | Rejection carries no reason; the customer-facing answer to a request is identical in every case; the masked log has the customer id only | `tests/customer-admin.test.ts` (reject notification, masked warning) |
| One-time codes read from the database | A copy of the OtpCode table lets an attacker recover the 6-digit codes | HMAC-SHA256 keyed by `OTP_PEPPER` (32+ bytes, different from both JWT secrets, validated at startup), bound to org, user and purpose; constant-time compare; 5 attempts spent before comparing | `tests/otp-hardening.test.ts` ("OTP_PEPPER") |
| Code flooding | Someone requests codes for an address (or many) to spam a mailbox or burn the email quota | Hourly caps per address (5) and per IP (20) in `config/otp-limits.ts`, counted whether or not the address exists; over the cap the answer is unchanged | `tests/otp-hardening.test.ts` ("hourly caps") |
| Email timing or failure reveals an account | A registered address answers differently or more slowly than an unknown or staff one | Email is queued and sent after the response; a failed or slow send never changes the answer; response floor; masked logs | `tests/otp-hardening.test.ts` ("email goes out only AFTER the response", "look the same") |
| Customer alert IDOR | Reading or marking another customer's alerts, devices or settings | Every query filters by org and the token's customer id; another's id is 404 (device) or changes nothing (mark-read) | `tests/customer-notifications.test.ts` (alerts, devices, preferences), mutation checks |
| Customer receives staff events | A customer stream shows a staff notification, or another org's | Separate route and guard; events are keyed by org and user; whitelisted fields; ends at token expiry; 3 streams per customer | `tests/customer-notifications.test.ts` ("the customer stream") |
| Push device takeover | A customer re-registers a staff member's device token and steals their pushes | A token held by a non-customer is refused | `tests/customer-notifications.test.ts`, `tests/db/customer-alerts.db.test.ts` |
| Presence write storm | A client calls the heartbeat in a loop to hammer the database | Write only if the stored value is older than 60 s; per-IP and per-customer rate limits | `tests/customer-notifications.test.ts` ("presence"), `tests/db/customer-alerts.db.test.ts` |
| Chat IDOR | A customer reads or writes another customer's (or org's) conversation, or links a chat to someone else's vehicle | Every lookup filters by org and the token's customer id; the vehicle must pass the customer visibility filter; the same 404 for unknown, foreign and unreleased | `tests/chat.test.ts` ("only your own conversations", "vehicle ownership"), `tests/db/chat.db.test.ts` |
| Chat injection | Markup, script, template or SQL text in a message executes in an app, a log or a query | Plain text stored as typed, only returned inside JSON, parameterised queries, control characters refused, no attachments, strict bodies (no sender or customer fields) | `tests/chat.test.ts` ("plain text, up to 2000 characters") |
| Chat flooding | A client floods staff with messages or alerts | 15 messages a minute, 10 new conversations an hour, 50 conversations, 2000 characters, one alert per burst | `tests/chat.test.ts` ("rate limits and caps", "a burst is one alert") |
| Message content leaves the app | The text of a message appears in a push, an email, an alert, a stream event or a log | Alerts use fixed text; stream events carry ids only (whitelisted fields); ActivityLog carries ids only | `tests/chat.test.ts` ("the alert for staff names the customer, not the message", "the stream only forwards whitelisted fields") |
| Wrong party receives a chat event | A customer sees staff-side events, staff of another org see a conversation, or the sender is told about their own message | Events are published per recipient user and org after commit: customer message to staff, staff reply to that customer | `tests/chat.test.ts` ("who is told, and how") |
| Staff chat by the wrong role | A VIEWER reads or answers customer chat, or an OPERATOR reaches a conversation of a customer who is not theirs | `CHAT_ROLES` in the auth hook; then `resolveScope` / `conversationScopeWhere` (the rule in `config/roles.ts`) on every request: the user's CURRENT role, `loginEnabled` and `assignedAgentId` come from the database, never a cached permission; out of scope is 404 | `tests/chat.test.ts` ("access", "operators reach only the conversations of customers assigned to them"), `tests/db/chat.db.test.ts` (operator scope on real SQL, 15 rounds of reassign + send), mutation checks |
| Alert to someone who cannot open the chat | A new-message alert, push or live event reaches a user who could not open that conversation | Recipients are the assigned agent only if active and their role may open chat, else active administrators and managers; the same list for events and alerts | `tests/chat.test.ts` ("a customer message alerts the assigned agent, else administrators and managers") |
| Price shown without its currency | A listing price reaches the website as a bare number and is misread, or a wrong currency is shown | The API only returns `price: { amount, currency: "LKR" }`; staff input is a positive whole number with a ceiling; the old field name and any currency field are refused | `tests/public-stock.test.ts` (key sets, "a price ..." validation), mutation checks |
| Public API exposes internal data | A public response contains internal ids, the org, drafts, sold stock, costs, serials or storage keys | A separate curated table, a fixed public filter (default org, PUBLISHED), DTOs built field by field, slug addressing, strict queries | `tests/public-stock.test.ts` ("what the public sees": key sets, 404 matrix), `tests/db/public-stock.db.test.ts` |
| Public API abuse | Scraping with a huge page size, probing with odd parameters, hammering the form | Page size capped at 24, strict parameters, per-IP read limit, form limits per minute / hour / email, 8 KB body limit | `tests/public-stock.test.ts` ("filters, sorting and paging", "rate limits") |
| Enquiry spam | Bots flood the form or use it to mail-bomb staff | Hidden-field honeypot (silent), strict zod limits, per-IP and per-email limits, optional Turnstile that fails closed, one fixed alert per enquiry | `tests/public-stock.test.ts` ("the enquiry form") |
| Enquiry content leaks | A visitor's message appears in a log, error, alert or ActivityLog | Nothing typed is logged or put in alerts; alerts carry the (cut) name only; parser errors are generic | `tests/public-stock.test.ts` ("never writes what the visitor typed") |
| Cross-origin abuse of the public API | Another site calls the public API from a browser, or the website reads the staff API | Per-route CORS allow-lists chosen by path, never `*`, no credentials, `Content-Type` only | `tests/public-stock.test.ts` ("headers: cache and CORS") |
| Private data cached publicly | An authenticated or private response becomes cacheable | `public, max-age=60` only on successful public stock GETs; everything else `no-store` | `tests/public-stock.test.ts` ("headers") |
| Stock image mix-up | A staff member registers another org's key, a private file or an SVG/HTML file as a public image | A separate public bucket and prefix; keys are issued by the API and must carry this org's hashed segment; jpeg / png / webp only; the listing is checked before the key | `tests/public-stock.test.ts` ("images") |
| Cross-org stock management | Staff of one org edit or publish another org's stock or images | Every lookup filters by the token's org (and the listing for image ids); 404 | `tests/public-stock.test.ts` ("another org's stock is a 404") |
| Cross-org or off-host file link for staff | A stored address pointing at another org's file, another host, a traversal path or a non-allowlisted type is signed and handed to a staff member | `signStaffFileUrl` derives the key with the SAME validated function as the customer gateway (the address must start with the configured public base AND the key with `org/<token's orgId>/`, allowlisted type); anything else is `url: null, unavailable: true` and only a masked count is logged | `tests/staff-signed-urls.test.ts` ("signStaffFileUrl", "GET /vehicles/:serial/files"); mutation checks on the host check and the org prefix |
| Signed link kept or leaked | A short-lived link is stored by a client, cached, or written to a log or error | Links live 60 to 900 s (`STAFF_SIGNED_URL_TTL_SECONDS`), the answer is `no-store`, clients are told not to store them; the redactor strips `X-Amz-Signature`, `X-Amz-Credential` and `X-Amz-Security-Token` from every log line and error; a signing failure returns null with the library's message dropped | `tests/staff-signed-urls.test.ts` ("signed-link secrets never reach a log or an error": real log and console output), mutation checks on the three patterns |
| Staff PDF export reads the public address | The export fetches the public address, which stops working (or is the wrong host) once the bucket is private | The server-side fetch uses the signed link on the storage host, after the same key validation, with redirects refused and size and time caps | `tests/staff-signed-urls.test.ts` ("pdf-images"), `tests/file.service.test.ts` |
| Bucket made private too early | Public access is switched off while a consumer still uses the public address | `npm run r2:audit` (read-only counts), the consumers checklist and the staged order in `docs/storage-migration.md`; rollback is re-enabling public access | `tests/staff-signed-urls.test.ts` ("npm run r2:audit"): counts only, no write calls, nothing sensitive printed |
| Storage references reach staff screens or logs | The main bucket's public address, an object key, a bucket name or the account id shows up in the activity log (admins), the upload answer or an error | New log entries hold a file's id, kind and name only (`lib/file-reference.ts`); everything the activity-log endpoints return is redacted at read time, old rows included, without rewriting history (`lib/storage-redaction.ts`); the upload presign returns `{ uploadUrl, key, expiresInSeconds, headers }` with no public address, and a file is registered by KEY (folder, characters, type, existence and size are checked, the stored address is built on the server) | `tests/storage-redaction.test.ts`, `tests/file.service.test.ts`, `tests/storage-signing.test.ts`, `tests/vehicle.write.service.test.ts` |
| The signed upload link shows the storage host | A staff member reads the account id and bucket name out of the presigned PUT link | **Accepted exposure.** The link is staff-only, valid 300 s, for one key, one type and one size, never logged (the redactor strips its signature) and answered `no-store`. Viewing links (the own-domain file links, docs/adr) will not contain a storage host | `tests/storage-signing.test.ts` (300 s, pinned size and type), `tests/staff-signed-urls.test.ts` (log redaction) |
| Wrong stock image address in production | The public stock image base is plain http, carries credentials, or is the throwaway r2.dev address in production | `PUBLIC_STOCK_IMAGE_BASE_URL` must always be an https address with no credentials, query or fragment; with `APP_ENV=production` an r2.dev host is refused at start with a clear message; in staging it gives one masked warning | `tests/app-env.test.ts` |
| Spoofed client IP | A client sends its own X-Forwarded-For or True-Client-IP to dodge the rate limit or to fake the address in a log | `CLIENT_IP_SOURCE` must be set explicitly in production (startup fails otherwise); `socket` ignores every forwarding header and logs one masked warning a minute if they are seen; `hops` trusts exactly TRUST_PROXY_HOPS proxies, never "trust all"; `header` reads one validated header, only for a host edge that overwrites it, and falls back to the socket address with a masked warning (no value logged) | `tests/trust-proxy.test.ts`, `tests/deployment.test.ts` ("client address modes"), `tests/startup-and-logging.test.ts` (production refusal, socket-mode warning), the self-test in `docs/runbook.md` |
| A viewer reads customers' contact details | A read-only VIEWER account (or a stolen one) lists every customer's email, phone and address, or probes them by searching | `canSeeCustomerContact(role)`: a VIEWER gets list rows and by-customer report groups without `email`, `phone` and `address` (the keys are absent), and the list's `q` matches the name only. Search and detail carry `{ id, name }` for every role. Other roles unchanged | `tests/viewer-privacy.test.ts` (exact key sets, search probing, report) |
| Personal data kept forever | One-time codes, old sessions, read alerts and abandoned sign-ups pile up with email addresses and device details | The daily job removes them after `RETENTION_OTP_DAYS` / `RETENTION_SESSION_DAYS` / `RETENTION_ALERT_DAYS` / `UNVERIFIED_ACCOUNT_DAYS`, batched, idempotent, scoped by org, one counts-only summary row per run. Chats and enquiries are kept (open question: docs/privacy-checklist.md). Dry run is the default (`RETENTION_DRY_RUN`), so nothing is removed until it is switched on; a customer is 'self-registered' only by a positive `CUSTOMER_REGISTER` record, never by 'unverified' alone | `tests/db/retention.db.test.ts` (each deletion, what it must keep, batch, idempotence, exact cut-off days), `tests/retention.test.ts` |
| A write that trusts the read before it | A bug or a race lets an id of another org reach an update or delete that only the earlier read had scoped | Every write carries org_id in its OWN where clause (`updateMany`/`deleteMany` with `org_id` and a count check: zero rows is a 404 and rolls the transaction back; lookup renames use the extended unique where `{ id, org_id }` and map P2025 to 404; photos and documents, which have no org column, are scoped through `vehicle: { org_id }`). Two writes are keyed by a secret the caller must hold and have no org to filter on: the refresh-token hash (logout) and the Expo push token (device registration) | `tests/org-scoped-writes.test.ts` (a static scan of every write in `src/`, the test database refusing an unscoped write in EVERY unit test, and 'the read lies' tests), `tests/db/org-scoped-writes.db.test.ts` (real Postgres) |
| Stale staff authorization | A deactivated, deleted or demoted staff user keeps using a 20-minute token, or an open stream, with the role it carried when it was issued | Every staff route and stream asks the database (`getFreshStaffAuth`): loginEnabled, user type, org and the DATABASE role decide; the token's role claim is never used. Cached for `STAFF_AUTH_CACHE_SECONDS` (default 30), cleared at once by every in-process create, edit, (de)activation and role change, with a generation counter against in-flight reads; streams re-check every 60 s without the cache and close when the user is disabled. Another instance sees a change within the cache time | `tests/staff-auth-freshness.test.ts`, `tests/route-inventory.test.ts` (every staff route: deactivated and unknown users 401, database role wins), `tests/db/staff-auth.db.test.ts` (real Postgres) |
| Request logs reveal what was searched or opened | A query string, a raw URL, a serial, a token or a client address in a request log line | Request lines carry method, route pattern, status, duration and request id only; redaction stays for tokens, hashes and signed-URL parameters | `tests/startup-and-logging.test.ts` (real log output), `tests/storage-signing.test.ts` |
| Native image library breaks the API | `sharp` fails to load on a host, taking the whole API down | `sharp` is imported lazily on the first thumbnail; on failure one masked error is logged, thumbnails are skipped and `thumb` requests get the full image | `tests/startup-and-logging.test.ts` ("the image library is optional") |
| Header-mode misconfiguration | The edge does not overwrite the client IP header, so clients choose their own address | Documented as safe only with an overwriting edge; a self-test with fake header values after every host change; the default stays `socket` | the runbook self-test (manual), `tests/deployment.test.ts` |
| Secrets baked into the image | A local `.env`, a dump or private notes end up in the container image | `.dockerignore` keeps every `.env*`, tests, docs, dumps and notes out; the Dockerfile copies named paths only; CI builds the image and fails if any `.env*` file is inside, or if it runs as root | `tests/deployment.test.ts` ("container files"), the CI `image` job |
| Install-time code | A dependency runs code while the image is built | `npm ci --ignore-scripts` everywhere in the image; the Prisma client is generated by an explicit command | `tests/deployment.test.ts` ("installs without running package scripts") |
| Unclean shutdown | A deploy kills the process mid-job or mid-stream, or hangs forever | SIGTERM handler with a deadline: stop accepting, `event: shutdown` to streams, bounded wait for a running job, close the pool, exit; a hang exits 1 at the deadline | `tests/deployment.test.ts` ("graceful shutdown") |
| Database latency script leaks | The latency tool prints the connection string or a driver error | Prints four numbers only; a fixed message on failure; read-only session; reads only DATABASE_URL | `tests/deployment.test.ts` ("database latency script") |
| Secret committed with --no-verify | Local hook skipped | The same scan (scripts/secret-scan.sh) runs as a required CI job over every tracked file | CI job `secret-scan` |
| Device token / bearer leakage | A push token or JWT inside an error message or log line | Errors are redacted before logging; token values are never echoed in responses | Device-token security tests |
| Device token probing | Hammering register/unregister | 20/min per IP on both endpoints; logout only removes the caller's own token | Rate-limit and logout-scoping tests |
| SSE cross-user leakage | A user opens a stream and receives another user's (or another org's) notifications | Events are delivered only to subscribers matching both userId and orgId, taken from the verified token; only whitelisted fields leave the server | SSE hub and integration tests (own events only; two orgs with the same user id) |
| Stale-token stream | A deactivated or revoked user keeps listening on a connection opened earlier | The stream closes at the access token's expiry (after `event: reauth`); the token must be in the Authorization header, never the URL | Token-expiry and query-string-token tests |
| Stream exhaustion | One client, or many connections, exhaust the server | Max 3 per user (oldest closed), global `SSE_MAX_CONNECTIONS`, slow clients dropped, 30/min per IP to open one | Eviction, cap and backpressure tests |
| Scheduler duplicate runs | Two instances, an overlapping trigger or a restart run the daily job twice | In-process overlap flag, Postgres advisory lock (transaction level), idempotent job body | Overlap, lock-not-acquired and multi-instance scheduler tests |
| Shared-secret job trigger | A leaked cron secret lets anyone run jobs | No shared secret exists: the manual trigger is ADMINISTRATOR-only with a bearer token and is logged with the actor | Admin job route tests (401, 403 per role) |
| Test harness aimed at a real database | A developer or CI sets TEST_DATABASE_URL to a real database and the harness drops its schema | Host must be localhost or the CI container; database name must start with `cargodev_test`; no host-override parameters; the database must be empty or harness-made (marker comment), which also catches a real database behind a tunnel; DATABASE_URL is never read | `tests/db-guard.test.ts` and the setup scenarios |
| Secret leakage | Token in logs or error body | Authorization header redacted; unexpected errors return generic `INTERNAL` | "Does not leak error message" test |
| Injection | Malicious input in a field | zod validation on all input; Prisma parameterised queries | Validation tests (400 + fieldErrors) |
| Overly broad CORS | Any website calls the API | Origin allow-list, never `*` | CORS test with unlisted origin |
| Production data damage | Migration run on shared DB | Separate dev DB; no `migrate` in this repo | Process rule + PR checklist |
| Vulnerable dependencies | Known CVE in a package | Dependabot, `npm audit` in CI, install scripts blocked by default | CI audit step |
