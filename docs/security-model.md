# Security model

Principle: security must not depend on the code being secret. Everything except keys can be public.

Each defence below must have a test. If you add a defence, add its row here.

| Threat | Example | Defence | Test that proves it |
|---|---|---|---|
| Cross-tenant access (IDOR) | Org A token requests an org B vehicle id | `orgId` from verified token on every query; other-org resource returns 404 | Two-org seed; org A token on org B ids expects 404 |
| Broken access control | VIEWER calls a mutation | Per-route role allow-list in the auth hook | 403 test per disallowed role per route |
| Missing authentication | Request with no/invalid token | Auth hook returns 401 | 401 test per route |
| Credential stuffing / brute force | Repeated login attempts | 5 failures lock the account 15 minutes; per-IP rate limit | Login lockout test |
| Token theft | Stolen access token | 20-minute access token; rotating, hashed refresh tokens; revoke on deactivation or password change | Refresh rotation + revoked token tests |
| Refresh token replay / race | A stolen refresh token used after the real client rotated it, or two requests rotating one token at once | Atomic claim of the old token; replaying a rotated token after a 10 s grace revokes all of the user's sessions | Concurrent-refresh and reuse tests |
| Account enumeration | Telling real emails from fake ones by response or timing | Unknown emails pay the same bcrypt cost and lock after 5 failures exactly like real accounts | Login-enumeration tests |
| Privilege escalation by renaming | A regular admin renames themselves to the reserved super-admin name | Reserved name (case-insensitive) rejected on create, staff update and own-profile update | Reserved-name tests |
| Stale sessions after access change | Admin resets a password, deactivates or changes the role of a user who still holds a refresh token | Those edits revoke the user's refresh tokens in the same transaction | Session-revocation tests |
| Cross-tenant references | Creating a model under another org's brand | Parent ids are checked against the actor's org (404) | Parent-ownership tests |
| Foreign ids in a vehicle write | A vehicle created or edited with another org's model, hall, supplier, customer or row colour, so reading it back joins that org's data | Every referenced id is checked against the actor's org (400) before the transaction | Foreign-id tests for create and update |
| Server-side request forgery via file URLs | A "photo" URL pointing at an internal address, later fetched by the PDF export | New file URLs must be under the configured public base and inside the caller's org folder; stored URLs are re-checked before any fetch; no redirects, size and time caps, images only | Object-storage URL tests; file service fetch tests |
| Cross-org object deletion | A photo URL pointing at another org's file, so deleting the photo deletes the real object | Same URL rule on the way in; deletion only ever touches keys inside the actor's own org folder | File service deletion tests |
| Double processing | Two daily runs, or a run racing an edit, flip a vehicle to Shipped twice | The transition is a conditional update on the current status; reminders are de-duplicated per vehicle and event per day | Daily checks real-database test |
| Accidental real email | A developer or CI run with a stray key sends mail to real people | One module (`src/lib/email.ts`) makes the only Resend call; it does nothing without `RESEND_API_KEY` and `EMAIL_FROM`; tests delete both variables; a test fails if any other file mentions Resend | `tests/email.test.ts` |
| Token audience confusion | A staff token used on customer routes, or a customer token on staff routes | Separate secrets, `aud` (staff / customer) and `iss` checked by each guard; startup fails if the secrets are equal | `tests/customer-zone.test.ts` (forged tokens in both directions) |
| Customer IDOR | One customer reading or changing another's data, or another org's | Customer id and org come only from the verified token; every query filters by both; strict bodies reject id and org fields; the guard re-loads the account each request | `tests/customer-zone.test.ts` (two customers in one org, two orgs) |
| One-time code brute force | Guessing a 6-digit code, in parallel | 5 attempts, each reserved atomically before the comparison; 10-minute life; single use; HMAC-stored; per-email and per-IP limits | `tests/customer-auth.test.ts`, `tests/db/customer-auth.concurrency.db.test.ts` |
| Account enumeration (customers) | Telling real addresses from fake ones by response or timing | Identical answers, a bcrypt compare or hash on every branch, a response-time floor, limits that count unknown addresses | Equality, bcrypt-count and floor tests |
| Pre-registration takeover | Registering a victim's address with a password the attacker knows | Register stores no password; it is set together with the emailed code | Verify-email tests |
| Customer data in logs | Passwords, codes, tokens or addresses reaching logs | Nothing logs them; email notices are masked; strict bodies | `tests/customer-logs.test.ts` (real log output) |
| File gateway abuse (customers) | A customer asks for a photo or document that is private, belongs to someone else, sits on a vehicle they may not see, or is not an allowed type; or hammers the endpoint | Authorise first (own vehicle, same org, not deleted, export track, released; file released), then read; every failure is the same 404 and nothing is read from R2; only jpeg/png/webp/pdf are served; rate limits per IP and per customer | `tests/storage-signing.test.ts` (gateway block), `tests/db/milestones.db.test.ts` |
| Storage key / URL leakage | An R2 address, an object key, the account id or the public base reaching a customer response, header, error or log | Files are addressed by database id; the API streams and never redirects; the stored URL is never in a DTO; the redactor scrubs R2 hosts, keys and the account id from logged errors; storage errors are a generic 500 | `tests/storage-signing.test.ts` ("NO customer response or log line contains...", "a storage error is a generic 500...") |
| Content sniffing / active content | An uploaded svg or html file served to a customer's app or browser and run | Allowlist of jpeg, png, webp, pdf at upload and again at serve time; the extension is forced from the signed type; `nosniff`, a sandboxing CSP and `inline` only for images | `tests/storage-signing.test.ts` (content types, headers) |
| R2 client pointed at the wrong endpoint | A misconfiguration sends requests (and credentials) to an AWS endpoint or an attacker's host | The endpoint is derived from a validated 32-hex account id; region `auto`; no AWS hostname in the code | `tests/r2-object-store.test.ts`, `tests/env-storage.test.ts` |
| Presign abuse | A client signs an upload for another org's vehicle, picks its own key or extension, or uploads a huge or wrong-type file | Vehicle ownership checked before signing; the server builds the key from a sanitised name with the extension of the signed type; the link pins size and type and lasts 300 s and requires no checksum headers; 10 MB images / 20 MB PDFs only; exact-match content types | `tests/storage-signing.test.ts` (presign block), `tests/r2-object-store.test.ts` |
| Double, lost or wrongly removed milestones | Two requests (or the job and a person) record the same milestone; a rolled-back change leaves one behind; clearing an ETD deletes something a person recorded | A unique key on (vehicle, type) with INSERT ... ON CONFLICT DO NOTHING in the status-change transaction; edits lock the vehicle row and decide from a fresh read; going down removes only milestones the system recorded and nobody touched, each with an ActivityLog row | `tests/milestones.test.ts` (every branch), `tests/db/milestones.db.test.ts`, `tests/db/milestones.concurrency.db.test.ts` (parallel set/clear of the ETD) |
| Backfill against the wrong database | The one-off backfill is pointed at production | It reads MIGRATION_DATABASE_URL only, is a dry run unless `--apply`, prints counts and the project ref only, and plans only milestones with a known date | `tests/milestone-backfill.test.ts` |
| Spoofed client IP | A client sends its own X-Forwarded-For to dodge the rate limit | Proxy headers are ignored unless TRUST_PROXY_HOPS says how many proxies we control; never "trust all" | Trust-proxy tests (hops 0, 1, 2) |
| Secret committed with --no-verify | Local hook skipped | The same scan (scripts/secret-scan.sh) runs as a required CI job over every tracked file | CI job `secret-scan` |
| Device token / bearer leakage | A push token or JWT inside an error message or log line | Errors are redacted before logging; token values are never echoed in responses | Device-token security tests |
| Device token probing | Hammering register/unregister | 20/min per IP on both endpoints; logout only removes the caller's own token | Rate-limit and logout-scoping tests |
| SSE cross-user leakage | A user opens a stream and receives another user's (or another org's) notifications | Events are delivered only to subscribers matching both userId and orgId, taken from the verified token; only whitelisted fields leave the server | SSE hub and integration tests (own events only; two orgs with the same user id) |
| Stale-token stream | A deactivated or revoked user keeps listening on a connection opened earlier | The stream closes at the access token's expiry (after `event: reauth`); the token must be in the Authorization header, never the URL | Token-expiry and query-string-token tests |
| Stream exhaustion | One client, or many connections, exhaust the server | Max 3 per user (oldest closed), global `SSE_MAX_CONNECTIONS`, slow clients dropped, 30/min per IP to open one | Eviction, cap and backpressure tests |
| Scheduler duplicate runs | Two instances, an overlapping trigger or a restart run the daily job twice | In-process overlap flag, Postgres advisory lock (transaction level), idempotent job body | Overlap, lock-not-acquired and multi-instance scheduler tests |
| Shared-secret job trigger | A leaked cron secret lets anyone run jobs | No shared secret exists: the manual trigger is ADMINISTRATOR-only with a bearer token and is logged with the actor | Admin job route tests (401, 403 per role) |
| Test harness aimed at a real database | A developer or CI sets TEST_DATABASE_URL to a real database and the harness drops its schema | Host must be localhost or the CI container; database name must start with `cargodev_test`; no host-override parameters; the database must be empty or harness-made (marker comment), which also catches a real database behind a tunnel; DATABASE_URL is never read | `tests/db-guard.test.ts` and the setup scenarios |
| Secret leakage | Token in logs or error body | Authorization header redacted; unexpected errors return generic `INTERNAL` | "Does not leak error message" test |
| Injection | Malicious input in a field | zod validation on all input; Prisma parameterised queries | Validation tests (400 + fieldErrors) |
| Overly broad CORS | Any website calls the API | Origin allow-list, never `*` | CORS test with unlisted origin |
| Production data damage | Migration run on shared DB | Separate dev DB; no `migrate` in this repo | Process rule + PR checklist |
| Vulnerable dependencies | Known CVE in a package | Dependabot, `npm audit` in CI, install scripts blocked by default | CI audit step |

## Accepted risks

Record any accepted `npm audit` finding here with the reason and a review date. Do not document known **unfixed** exploitable vulnerabilities in this public file; track those privately.
